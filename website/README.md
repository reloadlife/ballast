# Ballast website

Static Next.js App Router site for GitHub Pages. Bun, Turbopack, Tailwind CSS, a shadcn-style owned Button primitive, Motion, and a lazy-loaded Three.js scene. The native Swift app is unchanged.

## Local work

```sh
cd website
bun install --frozen-lockfile
bun run dev
# http://localhost:3000/ballast/
bun run build
bun run check
bun test
bun run preview
# http://127.0.0.1:4173/ballast/
```

`out/` is the deployable artifact. The preview serves the real export at the project subpath and returns the custom 404 for missing pages.

## GitHub Pages

The workflow `.github/workflows/website.yml` builds and validates pull requests. Pushes to `main` or manual workflow dispatch on `main` also deploy the artifact.

1. In repository Settings → Pages, select **GitHub Actions** as the publishing source.
2. Merge/push the website and workflow to `main`.
3. Verify the deployed site, all guide routes, and assets at `https://reloadlife.github.io/ballast/`.

No Pages site was configured at implementation time. A successful local build is not evidence of a live deployment.

## Future custom domain

Set the repository variable `BALLAST_SITE_URL` to the complete canonical HTTPS URL (for example `https://<your-domain>.app/`), configure that verified domain in GitHub Pages with its required DNS records, and rerun the workflow. `NEXT_PUBLIC_SITE_URL` controls both Next's basePath and every canonical, social-image, sitemap, and llms URL. Root-domain hosting uses an empty basePath. Do not set the new URL before the domain is ready. Enable HTTPS; `.app` requires it. Review GitHub's domain verification and DNS guidance before changing production.

## Search and answer-engine foundations

- Nine static, substantive public pages; unique titles/descriptions, canonical URLs, social previews.
- Visible answers mirrored in FAQPage JSON-LD; SoftwareApplication and Article/BreadcrumbList markup without fabricated ratings or reviews.
- Sitemap, ordinary crawlable links, semantic headings, accessible native disclosures, self-hosted fonts.
- `llms.txt` as an optional plain-text discovery aid; it does not guarantee ingestion or ranking.
- Google Search Console / Bing Webmaster verification and sitemap submission are post-deployment tasks. Neither SEO rankings, AI citations nor rich results can be guaranteed. Google does not require special AI markup: https://developers.google.com/search/docs/appearance/ai-features
- On GitHub project sites, `robots.txt` is at `/ballast/robots.txt`; crawlers generally consult the **origin-root** `/robots.txt`. The repo cannot control the account-root file. Use Search Console's sitemap submission and check origin policy after deployment. Custom-domain hosting serves this file at root.

### Visual and browser verification

With the production preview running, `bun scripts/browser-check.ts` uses installed Chrome (`CHROME_PATH` can override the executable) to check desktop/mobile rendering, runtime errors, horizontal overflow, live 3D controls, FAQ disclosure, axe accessibility, reduced motion, and HTML without JavaScript. Evidence is written to `/tmp/ballast-website-review/`. This is local browser proof, not physical-device or deployed-site proof.

The hero first paints `sculpture.webp` (about 14 KB), rendered from the actual authored 3D scene. Three.js and Motion load only on hover, keyboard focus, or activation. `sculpture-open.webp` provides a static fallback when WebGL cannot initialize. Regenerate both with `bun scripts/capture-sculpture.ts` against the running preview after changing geometry. The image metadata sidecars record provenance. The preview server uses gzip for text responses, as a production static host would; Lighthouse values are local lab measurements.
